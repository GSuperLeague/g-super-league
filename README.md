# G超联赛

桌面足球联赛管理网站，从原 Sites 项目迁移为独立 Git 仓库。支持单打、双打两个独立板块。

- [GitHub Pages](https://gsuperleague.github.io/g-super-league/)
- 前端：React + Vite，GitHub Pages 托管。
- 后端：你自己的 Cloudflare Worker + D1 数据库（含压缩头像）。
- 当前已配置独立数据服务：https://g-super-league-api.jason-brown-20-28-2023.workers.dev 。新部署到其他账号时，需设置自己的后端地址。管理员密钥须由账号所有者在 Cloudflare 中设置。

## 功能与规则

左上角切换单打 / 双打。单打球员独立登记，不要求加入球队；球员资料、头像、比赛、积分、段位分、历史交手及赛季设置均独立保存。双打保留原有球队、位置和搭档规则。

单打支持赛程、实时逐球记分、乌龙球、撤销、完赛与重新打开，以及赛后直接录入最终比分。只有已完赛比赛计入个人积分与段位分，单双打使用相同的段位规则。修改或删除历史比赛会重新计算后续评分。月份筛选内的评分从本赛季起始分重算；比赛详情展示本赛季完整历史下的当场段位分变化。乌龙球只统计明确事件，不从汇总比分推算。

### 赛季与新闻

- 按北京时间 `2026-11-02 00:00:00` 划分赛季：此前比赛归 beta赛季，此后归第一赛季。顶部可切换，球队积分、个人战绩、排行榜、事件和搭档分析都限于当前赛季。设置中的联赛标签不改变归属。
- 第一赛季公开段位分：`1200 + round(max(beta赛季 段位分 - 1200, 0) × 0.33)`。低于 1200 回到 1200；总分、前锋分、后卫分分别继承，单双打独立。新赛季积分、胜负、进失球从零累计，未出场也显示继承分。
- 隐藏 MMR：`1200 + (beta赛季 MMR - 1200) × 0.33`，保留完整精度，允许低于 1200，不在界面展示。赛季内沿用原有结算规则。
- 历史比赛保存在原始记录中，赛季视图和继承分实时派生，无需清库或数据库迁移。修改 beta赛季 记录会重算其终榜及第一赛季继承；第一赛季结果不会改变 beta赛季。JSON 导出始终包含全部赛季和新闻。
- 联赛新闻支持检索、赛季筛选和管理员发布、编辑、删除。双打 beta赛季 定榜稿按历史数据生成，包含 TOP3、金乌龙、搭档、前锋、后卫、宿敌、快乐搭档、韧性、被逆转、劳模和年度逆转奖项，以及五场不同比赛的单场高光、关键比分和比赛回查。劳模按完赛出场数、年度逆转按胜方最大落后分差评选，均支持并列。金乌龙按场均乌龙排名，仅使用有逐球记录的完赛，至少 3 场；汇总比分不作乌龙或领先过程推算。管理员可编辑定榜稿，删除编辑版本可恢复自动稿。
- 新闻保存使用现有 Worker 的 `news.save` / `news.delete` 操作，受原管理员权限保护，单双打各自存储。上线时须同时部署更新后的 Worker；没有新的 D1 表或远程数据导入步骤。

球队登记、球员编辑、多球队成员关系、球员画像、虚拟身价、赛程、赛前阵容登记、实时逐球记分、乌龙球榜与事件明细、赛后直接登记最终比分、球队积分榜、射手与防守榜、个人与分位置表现、双人搭档、同阵容换位对照、历史交手、三套段位分、段位徽章、单场段位分变化、三种数据雷达、赛场荣誉、JSON 导出、每 3 秒同步。

- 球员档案的「每场加减分」按最近在前展示当前赛季的完赛结算：加减分、赛前与赛后分数、比分、对手及本场位置，点击可回查比赛。双打随总览 / 前锋 / 后卫切换，单打独立展示；默认 10 场并可继续展开。累计变动不含赛季继承，未计分记录显示「—」，不当作 0 分结算。
- 常驻队比赛计入球队战绩、个人及组合数据；临时组队的比赛卡片与详情比分区显示本场前锋、后卫姓名，未记录位置时只列出场球员；计个人及组合，不计球队战绩。
- 比赛中心 →「新建实时比赛」，登记每队前锋和后卫，可保存赛程或直接开赛；比赛中点击得分方 +1，选择实际进球人。完赛后按登记位置更新段位分和搭档分析。原赛后录分入口保留。
- 乌龙球：点击受益方 +1，勾选「这是对方乌龙球」，选择实际踢出乌龙球的对方球员；给受益方加分，不计正常个人进球。乌龙球页统计进行中及已完赛的明确事件，支持榜单、搜索、明细和比赛回查。撤销、改正、删除比赛都会重新计算；历史汇总比分不推算乌龙球。
- 球员总览和位置统计包括出场、胜平负、胜率、球队得失分、净胜球、场均表现、关键局、连胜和最近 10 场。
- 得失分统计球员在场时的球队比分。射手榜沿用原记账口径：赛后汇总将本队进球计给本场前锋；逐球记录使用实际指定球员，乌龙球不计个人进球。前锋记账不代表实际逐球归属，不由汇总推算助攻、扑救、逆转等事件指标。
- 射手榜累计进球包含进行中比赛；场均进球使用已完赛且记录前锋位置的比赛，分子为这些比赛中该球员的记账进球，分母为前锋场次。防守榜统计后卫角色明确的完赛比赛，防守球为该场全队净胜球，沿用原榜单口径。
- 前锋、后卫表现使用本场明确记录的角色，不依据当前球员资料推测历史位置。未完赛比赛不计入统计。
- beta赛季 展示段位分与内部 MMR 均从 1200 开始，第一赛季按上述公式继承，无定级赛；总分、前锋、后卫各自独立回算。段位分最低 0，未参赛也显示赛季起始分。
- 相对净胜球倍率 `M = 1 + 0.5 × |主队得分 − 客队得分| / max(主队得分, 客队得分)`，0:0 时取 1。7:0 与 10:0 使用相同倍率 1.5。
- 内部 MMR 使用 Elo：`64 ×（赛果 − 预期胜率）× M`，赛果为胜 1、平 0.5、负 0，预期胜率分母尺度 400，保留完整精度。较大的 K 值让实力估计更快响应赛果，不引入定级赛。双打比较两位队员赛前 MMR 均值，同队两人获得相同 MMR 变化；位置计算只更新本场角色。MMR 保持零和，不要求与带成长奖励的段位分完全相等，也不在页面、雷达、历史轨迹或单场结算中展示。
- 段位分基础收益随个人赛前分数连续变化：1000 分及以下胜 +36 / 负 −10 / 平 +6，1100 分 +34 / −12 / +5，1200 分 +32 / −14 / +4，1300 分 +28 / −18 / +3，1400 分及以上统一 +24 / −24 / 0。各节点之间线性插值，跨段位不会突然改变结算。上述为对手实力相当、个人段位分与 MMR 相等、净胜球倍率为 1 的参考值；黄金及以下更容易成长，钻石基础胜负对称，大师、宗师、王者不额外加重扣分。
- 成长目标为从 1200 出发，约 50% 胜率打二十多场后到铂金附近。以 24 场 12 胜 12 负、随机胜负顺序、双方赛前实力相当、胜负使用相同净胜倍率回放，7:6、8:5、10:0 三种比分情景的中位数约为 1298–1304。该目标不是定级或保底；对手强弱、比分和赛果顺序仍会影响最终分数。
- 用赛前预期胜率 `p` 对基础收益加权：胜场 `W × 2 × (1 − p)`，负场 `−L × 2 × p`，平局 `D + (W + L) × (0.5 − p)`；W、L、D 来自上述分数曲线，L 为正数。个人追赶修正为 `clamp((赛前 MMR − 赛前段位分) / 25, −8, 8)`，加入修正后胜场变化最低 0、负场变化最高 0，平局可加分或扣分。最终变化 `round(修正后变化 × M)`，再应用最低 0 分。取整采用正负对称的四舍五入（−22.5 取 −23），中间值不提前取整。战胜强队更有收益，段位领先实力且反复战胜明显弱队时可能加 0 分，避免靠刷弱队持续膨胀。全部使用赛前值；段位分不要求零和，与传统联赛积分独立。
- 段位：0–999 黑铁、1000–1099 青铜、1100–1199 白银、1200–1299 黄金、1300–1399 铂金、1400–1499 钻石、1500–1599 大师、1600–1699 宗师、1700 及以上王者。分数旁显示对应徽章，悬停可查看段位与段内进度。
- 传统榜单、人工能力、身价和当前常用位置不参与评分。比赛先后顺序、历史赛果及当场阵容与角色会影响回算；临时组队与常驻队完整记录位置的 2 对 2 完赛都计分。
- 打开比赛可切换总段位分和位置段位分，查看四名球员赛前、赛后及变化值。未完赛或阵容不完整时不生成赛后变化。
- 数据页支持比赛类型、北京时间月份与最少出场筛选。评分随筛选范围从本赛季起始分重新计算；不足 3 场标为小样本但正常排名，无样本统计项显示「—」。
- 双人组合只统计同侧恰好两位球员的比赛；可查看胜率矩阵、进攻及防守组合榜。球员与球队交手记录均可下钻到比赛。
- 前后位置搭档矩阵区分「甲前锋 / 乙后卫」与反向站位。同阵容换位对照固定同一对搭档、对方两人及对方位置，两种站位均需达到出场门槛，可查看对应比赛。
- 位置对照展示逐场得分占比的平均值（0:0 排除）、Wilson 95% 胜率区间、搭档和对手人数，以及有效计分场次的搭档、对手赛前总段位分均值。上述统计提供阵容和样本背景，不参与结算；源数据未记录分制、球桌及先后手，无法完全控制这些差异。
- 球员档案有总览、前锋和后卫三种雷达图，算法与原值可在页面「统计口径与评分」查看；人工能力值作为原始资料保留。
- 赛季或月度 MVP、最佳位置和最佳搭档要求至少 3 场有效样本。缺少事件记录的奖项不生成。
- 编辑比分会替换原结果；删除比赛后榜单重新计算；更改球员常用位置不改变历史比赛角色。
- 身价和人工能力资料由管理员维护；赛果雷达与段位分自动计算。

## 部署

### 1. 安装与准备

需要 Node.js 22.13+、npm、Git，以及你自己的 Cloudflare 账号（启用 Workers、D1）。

```bash
git clone https://github.com/GSuperLeague/g-super-league.git
cd g-super-league
npm ci
npx wrangler login
cp backend/wrangler.example.jsonc backend/wrangler.jsonc
npx wrangler d1 create g-super-league
```

将创建 D1 时返回的 `database_id` 填入 `backend/wrangler.jsonc`。该文件虽使用 `.jsonc` 扩展名，请保持标准 JSON（迁移脚本会读取它）。配置文件被 Git 忽略。

`ALLOWED_ORIGINS` 使用网站**来源**而非含路径的网址，默认是 `https://gsuperleague.github.io,https://junjieyu28.github.io,http://localhost:5173`。使用自定义域名时同步更新这里。

### 2. 发布数据服务

```bash
npm run db:remote
npm run api:deploy
npx wrangler secret put ADMIN_TOKEN --config backend/wrangler.jsonc
```

按提示输入你自行生成的至少 24 字符随机管理密钥，妥善保管并交给记录员。它只保存在 Worker secret 中；不要写入 Git、Vite 环境变量或 README。未设置有效密钥时写入会被拒绝，读取仍开放。记录员在右上角「管理员登录」输入密钥，浏览器只在当前标签页 sessionStorage 保存；退出管理即清除。所有访客都可查看联赛数据。

记下 Wrangler 返回的 HTTPS Worker 地址。

### 3. 迁移旧数据

在旧站停止新增登记期间执行，避免迁移过程中两边继续修改造成遗漏。原站不会被修改或删除。

```bash
SOURCE_URL=https://g-super-league.luke19929788.chatgpt.site npm run backup
npm run restore
```

导出内容放在 `.migration/backup.json` 和 `.migration/photos/`，含球队、球员、比赛、设置与头像原文件；这些个人数据不会进入公共仓库。`restore` 使用原头像 ID，且仅允许导入空联赛，拒绝覆盖已有记录。导入后核对人数、场次和榜单，再切换使用新网站。若旧站访问权限改变，需先恢复可读取的导出来源，或使用先前保存的完整备份。

2026-10-19 已将 4 支球队、5 名球员、8 场比赛导入独立 D1 数据库（当时没有头像）。后续迁移应重新导出最新快照。

### 单打数据库与现有部署升级

单打必须新建独立的 **D1 数据库**，不能复用双打的 `database_id`。两库沿用相同的 `league` / `photos` 表结构；各自保存 `id=main` 的联赛 JSON 和独立 `revision`，单打 JSON 额外带有 `mode: "singles"`。单打 API 为 `/api/singles/league`、`/api/singles/photos` 和 `/api/singles/auth`，双打原有 API 不变。

已有线上双打部署时，在原 Cloudflare 账号中执行：

```bash
npx wrangler login
npx wrangler d1 create g-super-league-singles
```

保留 `backend/wrangler.jsonc` 中原有 `DB` 的配置，按 `backend/wrangler.example.jsonc` 增加 `DB_SINGLES`，填入新库 ID，并将 `migrations_dir` 设为 `migrations`。随后执行：

```bash
npm run db:singles:remote
npm run api:deploy
```

全新部署还需先创建并初始化双打 `DB`。`api:deploy` 会校验两个真实数据库 ID 不同。单打未配置时接口返回 503，不回退到双打库；单打头像始终使用自己的 D1，即使双打启用了 R2。

默认两种模式使用同一个 Worker 管理密钥，但浏览器登录状态分别保存。需要独立单打密钥时执行：

```bash
npx wrangler secret put SINGLES_ADMIN_TOKEN --config backend/wrangler.jsonc
```

GitHub Pages 工作流只发布前端，**不会自动创建 D1 或部署 Worker**。应先完成以上后端升级，再发布前端。GitHub 仓库写权限与 Cloudflare 权限独立。

单打完整备份（含头像）与空库恢复使用独立目录 `.migration/singles/`：

```bash
LEAGUE_MODE=singles SOURCE_URL=https://你的后端地址 npm run backup
LEAGUE_MODE=singles npm run restore
```

不设置 `LEAGUE_MODE` 时继续使用原有双打备份流程；恢复时拒绝单打、双打备份混用。页面导出只包含当前板块 JSON 和头像链接，不含图片文件。

### 4. 连接 GitHub Pages

本仓库工作流已配置当前后端的默认地址。更换后端时，可在仓库 Settings → Secrets and variables → Actions → **Variables** 新增覆盖值：

| 名称 | 值 |
|---|---|
| `VITE_API_BASE_URL` | 上一步 Worker 的 HTTPS 地址，不带 `/api` |

Settings → Pages → Source 选择 **GitHub Actions**。Actions → Deploy GitHub Pages → Run workflow。推送到 `main` 也会自动测试、构建并发布。

网站路径默认 `/g-super-league/`。如果以后迁到用户根站或改仓库名，修改 `.github/workflows/pages.yml` 的 `VITE_BASE_PATH`。修改 Actions 变量后必须重新运行工作流，变量才会进入新的静态构建。

没有管理密钥会返回 401；来源配置不匹配会返回 403；数据库未初始化时会返回 503。请勿把旧站地址用作新后端，它仍依赖原托管，并且没有新接口所需的跨域配置。

头像默认存储在 D1 的 `photos` 表，客户端压缩到最长边 512 像素，上传限制 1MB。无需 R2 订阅。需要更大规模时，可在配置中加入绑定名为 `BUCKET` 的 R2 桶；接口和迁移脚本仍支持 R2。

## 本地开发

### 空库预览与单打浏览器测试

```bash
npm ci
npm run dev:snapshot
```

不传快照时启动本地 Worker 和 Vite，自动初始化两个独立的本地数据库，保留已有本地记录。访问终端输出的 URL；本地管理密钥为 `preview-only-admin-token-2026`，两种模式分别登录。此模式不需要 Cloudflare 登录，也不会写入线上数据库。

服务器运行后，另开终端执行：

```bash
npx playwright install chromium
npm run test:e2e
```

浏览器测试仅允许本地地址，覆盖球员登记和头像、记分/乌龙球/撤销、完赛与改分、段位分、交手记录、数据导出、单打/双打隔离及桌面/390px/320px 布局。测试会清理自己创建的球员和比赛；截图保存在忽略目录 `.migration/browser-checks/`。端口非 5173 时设置 `GSL_LOCAL_FRONT_PORT`，或使用 `E2E_BASE_URL` 指定完整本地前端地址。

用含有完整双打赛果的快照启动预览后，可运行 `npm run test:e2e:rank`。该只读测试检查总榜、位置榜、球员档案、单场结算、段位徽章与分数一致性，确认页面不展示 MMR，并检查桌面/390px/320px 布局。

### 后端无法连接时：导出数据、本地预览

在能访问线上数据的浏览器中，进入「联赛设置 → 导出数据快照」，将 JSON 放到仓库根目录。开发机无需连接线上后端，直接启动本地 demo（Node.js 22.13+）：

```bash
npm ci
npm run dev:snapshot -- G超联赛-2026-10-19.json
```

脚本初始化独立的本地 D1，启动真实 Worker 和 Vite，默认访问 `http://localhost:5173/g-super-league/`。端口占用时自动选空闲端口，以控制台输出为准。远程开发机可转发前端端口；API 经 Vite 同源代理，无需额外转发。

启智 Notebook 环境会额外输出包含当前实例路径的 `Notebook 预览` 完整链接，请使用该链接。仅用域名加 `/proxy/5173/` 会在平台网关返回 404。开发预览自动保留代理路径，用于加载页面资源、API 和热更新；生产构建仍使用 GitHub Pages 路径。

Notebook 端口代理只负责打开开发服务器，不等于访问线上接口的网络代理。如需连接线上后端，应在实际发请求的浏览器或主机配置网络代理，确认 `/api/league` 能访问；仅设置终端代理不会让浏览器自动走代理。返回 403 时检查后端 `ALLOWED_ORIGINS` 是否包含当前页面来源。快照模式不依赖线上接口或其网络代理。

本地管理密钥为 `preview-only-admin-token-2026`，仅用于本地 Worker。可登录后测试录入、编辑、删除；所有更改保存在 `.migration/local-preview/`，再次运行命令时会恢复到传入的快照。JSON 中的头像是链接，不含原图。

该模式只运行本地服务，快照与本地数据库不打包进前端，也不写入线上数据。导出的 `G超联赛-*.json` 已加入 Git 忽略规则。单打快照根据 `mode: "singles"` 导入单打本地库；其他快照导入双打本地库，不覆盖另一板块。

预览确认后运行 `npm test`、`npm run build`，再提交并 `git push origin main`；GitHub Actions 发布前端代码，线上联赛数据保持独立。
